Recommendation: Redis with a 5-minute TTL, CDN for static assets

7 of 10 agents converged on Redis. The Haiku arguers surfaced one real dissent: in-memory is sufficient for single-instance workloads under 50 req/s. The Gemini contrarian flagged CDN edge caching as underexplored. Both are judgment calls for the team, documented below.

Section 01 — Where they agree

Must-fix findings (all or majority agree)

Critical
No TTL set on current cache keys

8 of 10 agents flagged this independently. Keys written by the auth service have no expiry. A session invalidation event leaves stale tokens in cache indefinitely. Fix before any cache strategy ships.

Critical
Cache stampede unguarded on cold start

Finder-2 and Gemini both caught this. On cold start, 100+ concurrent requests hit the origin simultaneously. No mutex or probabilistic early expiry in place. Redis or in-memory, same risk either way.

Warning
Serialization format not pinned

Finder-1 and Finder-3 noted the cache currently uses JSON.stringify. If object shape changes, deserialization silently returns wrong data with no error. Pin a versioned schema or add a version prefix to all keys.

Note
Redis client not reused across requests

Finder-4 only. New client instantiated per request in the middleware. Not a correctness bug but will exhaust connection pool under load. Move to a singleton at module scope.

Section 03 — Where they split

Judgment calls for the team

Is the workload single-instance or multi-instance now?
Finder-3 + Arguer-2

Current infra is a single Fly.io machine. Redis adds a network hop and a dependency for a problem that doesn't exist yet. In-memory is correct for the actual workload.

Finder-1, Finder-2, Finder-4

Scaling to two machines without shared cache will produce split-brain session state. The cost of Redis on Fly is $1.94/mo. Pay it before you need it.

Lead call

Take Redis. The counter-argument is correct on current state, but the migration cost from in-memory to Redis mid-scale is high and the preventative cost is near zero. Finder-3's position is right for a prototype; this is production.

Should CDN edge caching replace Redis for read-heavy routes?
Gemini contrarian

The /api/listings route is 90% reads, public, and already behind Cloudflare. A Cache-Control header ships the CDN solution in an afternoon. Redis can't get you sub-10ms from a regional PoP.

Finder-2, Arguer-1

Listings include personalized sort order based on user session. CDN caching a personalized response is a privacy bug waiting to happen. Vary header complexity is non-trivial.

Lead call

Gemini's point is valid for the unauthenticated public feed. Finder-2 is right for the personalized view. Both can coexist: CDN on public routes, Redis on session-aware routes. Gemini surfaced a real optimization the Sonnet line missed.
